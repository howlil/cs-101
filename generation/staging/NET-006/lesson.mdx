> **Masalah:** API tidak menerima request meskipun proses backend berjalan. Apakah TCP tidak terbentuk, data harus dikirim ulang, atau koneksinya justru sudah ditutup?

**Langkah pertama:** gambar `SYN → SYN-ACK → ACK`. Labeli client, server, source/destination IP dan port. Handshake ini terjadi pada TCP sebelum payload aplikasi dapat diterima sebagai stream terhubung.

<MentalModel title="TCP adalah byte stream dengan state, bukan rangkaian HTTP status">

- **Handshake:** SYN mengumumkan *initial sequence number* (ISN), SYN-ACK mengakui ISN client dan mengumumkan ISN server, ACK client mengakui ISN server.
- **Acknowledgment:** ACK berisi nomor *byte berikutnya yang diharapkan*. SYN dan FIN masing-masing mengonsumsi satu posisi sequence space, sedangkan ACK tanpa data tidak.
- **Data:** TCP memberikan byte berurutan; satu pemanggilan `socket.write()` tidak harus menjadi satu paket ataupun satu callback `data`.
- **Retransmission:** data yang belum diakui dapat dikirim ulang melalui mekanisme RTO; apakah retransmission benar-benar terjadi harus dibuktikan pada capture.
- **Close:** FIN menutup satu arah pengiriman, RST membatalkan koneksi; listener yang sudah berhenti dapat menolak koneksi baru.

</MentalModel>

## Membaca sequence dan ACK

Jika client memulai `SYN seq=100` dan server merespons `SYN+ACK seq=300 ack=101`, ACK client untuk SYN server adalah `ack=301`. Wireshark sering menggunakan **relative sequence numbers**, jadi nilai awal dapat tampil sebagai `0` dan ACK berikutnya `1`. Selalu jelaskan apakah tampilan memakai relative atau absolute sequence numbers.

Packet loss dan congestion dapat menyebabkan retransmission, tetapi *tidak otomatis terjadi* saat eksperimen lokal. RFC 6298 mengatur retransmission timeout dan backoff; repeated SYN atau data tidak membuktikan HTTP 503 tanpa respons HTTP yang benar-benar diterima.

## Project — TCP Handshake Capture

<LearningSegments stage="evidence" segments={lessonSegments} />

Gunakan hanya VM lokal atau network namespace yang kamu miliki. Pada terminal pertama, jalankan listener berikut dan biarkan aktif:

```sh
node -e "require('node:net').createServer(s=>s.end('ack')).listen(4040,'127.0.0.1')"
```

Pada terminal kedua, mulailah capture **sebelum client connect** (Linux, antarmuka loopback `lo`):

```sh
sudo tcpdump -i lo -nn -s 0 -w /tmp/tcp-handshake.pcap 'tcp port 4040'
```

Pada terminal ketiga, buat koneksi singkat:

```sh
nc 127.0.0.1 4040
```

Hentikan capture setelah koneksi berakhir, lalu analisis pcap di Wireshark atau baca ulang menggunakan `tcpdump -nn -S -r /tmp/tcp-handshake.pcap`. **Jangan mengasumsikan retransmission ada** pada loopback. Jika tidak terjadi, dokumentasikan bahwa capture tersebut tidak mengandung retransmission dan jelaskan satu skenario retransmission berdasarkan RFC 6298 secara terpisah. Modifikasi packet loss hanya pada VM atau namespace disposable, bukan jaringan production.
