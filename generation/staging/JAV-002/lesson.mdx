> Dua transaksi dengan ID yang sama harus dikenali sebagai **nilai yang sama**, meskipun dibuat sebagai object berbeda. Tetapi transaksi dengan ID kosong tidak boleh pernah tercipta. Desain objek yang benar menjaga dua hal itu sejak konstruksi.

## Setelah materi ini, lo harus bisa

- menyatakan invariant yang menjadi tanggung jawab suatu object dan menolak konstruksi tidak valid;
- membedakan encapsulation, abstraction, interface, polymorphism, dan composition;
- memilih record untuk immutable value object, sekaligus mengenali batas *shallow immutability*;
- memprediksi `==`, `equals`, `hashCode`, dan `toString`;
- menguji bahwa `HashMap` dan `HashSet` memperlakukan key yang setara dengan benar;
- menyuntik satu cacat equality/hash lalu melihat test gagal dengan alasan yang tepat.

## Prasyarat

Lanjutkan dari [JAV-001 — Java toolchain + language model](/learn/JAV-001): reference, `null`, records dasar, dan build/test Maven. Materi ini memakai konsep itu untuk merancang kontrak object; tidak mengulang setup JDK.

## 1. Encapsulation menjaga invariant

*Encapsulation* bukan sekadar mengubah field menjadi `private`. Ia membuat satu boundary yang memutuskan **state mana yang boleh ada** dan operasi apa yang boleh mengubahnya.

```java
public record AccountId(String value) {
    public AccountId {
        if (value == null || !value.matches("acct-[a-z0-9]+")) {
            throw new IllegalArgumentException("Invalid account ID");
        }
    }
}
```

Dengan constructor itu, `new AccountId("acct-7")` valid, sedangkan `new AccountId("")`, `new AccountId(null)`, dan `new AccountId("user-7")` gagal. Yang penting bukan regex spesifiknya, melainkan **aturan domain disimpan di pemilik data**, bukan diduplikasi dalam controller, parser, dan service.

*Abstraction* adalah kontrak yang mengekspos hal relevan kepada pemakai dan menyembunyikan detail yang tidak perlu. `AccountId` mengekspos `value()` dan semantik kesetaraannya; caller tidak perlu tahu langkah validasinya.

## 2. Interface, polymorphism, dan composition

Interface menyatakan kemampuan. Client menerima kemampuan itu sebagai dependency, bukan membangun subclass khusus untuk setiap perilaku.

```java
interface ReceiptFormatter {
    String format(AccountId accountId);
}

final class ReceiptService {
    private final ReceiptFormatter formatter;

    ReceiptService(ReceiptFormatter formatter) {
        this.formatter = java.util.Objects.requireNonNull(formatter);
    }

    String receiptFor(AccountId id) {
        return formatter.format(id);
    }
}
```

`ReceiptService` **memiliki** sebuah formatter (*composition*); bukan **merupakan** formatter (*inheritance*). Dua implementasi `ReceiptFormatter` dapat dipertukarkan, dan pemanggilan `format` memilih implementasi konkret di runtime (*polymorphism*). Gunakan inheritance hanya saat relasi *is-a* dan substitusi benar-benar berlaku, bukan untuk berbagi beberapa baris kode.

<Reveal title="Tes mental model: kapan butuh subclass?">
Jika kebutuhan hanya mengganti format receipt, interface + composition lebih kecil coupling-nya: `ReceiptService` bergantung pada `ReceiptFormatter`. Subclass `ReceiptService` untuk setiap format justru mengikat variasi formatting pada lifecycle service.
</Reveal>

## 3. Record adalah value carrier, bukan validasi otomatis

Record membuat component field `final` dan menyediakan accessor serta implementasi `equals`, `hashCode`, dan `toString` berdasarkan component. Akan tetapi, record **shallowly immutable**: bila component menunjuk `List` mutable, isi list masih bisa berubah.

```java
record TransactionId(String value) {
    TransactionId {
        if (value == null || !value.matches("tx-[a-z0-9]+")) {
            throw new IllegalArgumentException("Invalid transaction ID");
        }
    }
}
```

`String` immutable, sehingga component di atas aman terhadap mutation dari luar. Sebaliknya, `record Basket(List<String> entries) {}` **bukan** deeply immutable; caller dapat mengubah list. Jika suatu value object perlu collection, buat defensive copy saat konstruksi dan pastikan accessor tidak membocorkan struktur mutable. Ini perlu keputusan per tipe, bukan aturan bahwa semua record otomatis aman.

Untuk `Money`, pilih representasi exact yang disengaja. Pada latihan ini gunakan `long minorUnits` bersama currency code; *jangan* menjadikan `double` sebagai amount finansial. Tetapkan invariant dengan jelas: currency wajib tersedia dan berbentuk kode yang didukung; apakah nilai negatif boleh ada bergantung apakah `Money` berarti nominal pembayaran atau perubahan saldo. Jangan menyembunyikan keputusan domain itu di formatter UI.

## 4. Identity berbeda dari equality

```java
var first = new AccountId("acct-7");
var second = new AccountId("acct-7");

System.out.println(first == second);      // false: dua object
System.out.println(first.equals(second)); // true: nilai sama
System.out.println(first.hashCode() == second.hashCode()); // true
```

`==` pada reference menanyakan apakah kedua variable menunjuk object yang sama. `equals` menanyakan kesetaraan menurut kontrak class. Dua `AccountId` dengan nilai sama harus setara; `AccountId("acct-7")` dan `TransactionId("tx-7")` adalah tipe domain berbeda, bukan identitas yang dapat dipertukarkan.

## 5. Kontrak `equals`, `hashCode`, dan `toString`

Kontrak `equals` untuk referensi non-null meliputi **reflexive** (`a=a`), **symmetric** (`a=b` berarti `b=a`), **transitive** (`a=b` dan `b=c` berarti `a=c`), **consistent**, dan `a.equals(null) == false`.

Jika `a.equals(b)` benar, `a.hashCode() == b.hashCode()` **wajib** benar. Kebalikannya tidak wajib: hash collision boleh terjadi. `toString` bertujuan memberi representasi yang berguna untuk debugging; ia bukan dasar equality dan formatnya tidak seharusnya menjadi kontrak serialisasi tanpa spesifikasi eksplisit. Hindari menyertakan rahasia dalam outputnya.

<ConceptGraph>
<pre>{`equals(a, b) = true
        ↓ wajib
hashCode(a) = hashCode(b)
        ↓
hash-based lookup mencari kandidat pada kelompok hash
        ↓
equals memastikan key yang benar

hashCode(a) = hashCode(b) ⇏ equals(a, b)`}</pre>
</ConceptGraph>

## 6. Mengapa HashMap bisa tampak kehilangan key?

`HashMap` memakai hash key untuk memilih lokasi pencarian, kemudian equality untuk mencocokkan key. Bila dua key yang secara logis sama menghasilkan hash berbeda, pencarian bisa melewatkan key yang sudah disimpan. Bila key dimutasi setelah dimasukkan sehingga hash berubah, lookup dengan key itu juga bisa gagal. Inilah alasan invariant dan immutability merupakan masalah correctness, bukan sekadar gaya OOP.

```java
var byAccount = new java.util.HashMap<AccountId, Integer>();
byAccount.put(new AccountId("acct-7"), 10);

System.out.println(byAccount.get(new AccountId("acct-7"))); // 10
System.out.println(byAccount.size());                         // 1
```

`HashSet` memakai semantik key yang setara untuk deduplikasi. Ia tidak menjamin urutan iterasi. Detail algoritma internal dan kompleksitas koleksi diperdalam pada [JAV-003 — Collections + Generics](/learn/JAV-003).

## Tiga prediksi sebelum latihan

1. Dua `new TransactionId("tx-1")` berbeda reference. Apakah `HashSet` berisi satu atau dua elemen setelah keduanya ditambah?
2. Dua key punya `equals == true`, tetapi `hashCode` berbeda. Apakah `HashMap.get` dijamin menemukan value dari key pertama saat dicari memakai key kedua?
3. Sebuah `record Payload(List<String> values)` dibuat dari list mutable. Apakah perubahan isi list sesudah konstruksi pasti ditolak compiler?

<Reveal title="Periksa prediksimu">
1. **Satu**, karena record tersebut menerapkan value equality. 2. **Tidak**; kontrak hash rusak dan lookup tidak dapat diandalkan. 3. **Tidak**; reference field-nya final, tetapi object list masih mutable.
</Reveal>

## Guided practice — tiga langkah, satu hasil

**Langkah 1 — Invariant.** Buat tiga value object: `Money`, `AccountId`, dan `TransactionId`. Tentukan dan tulis tabel valid/invalid **sebelum** mengimplementasikan compact constructor/factory. Jalankan test untuk semua input invalid yang didaftarkan. Untuk `Money` gunakan exact minor units + currency, tanpa floating-point amount; untuk ID gunakan format yang eksplisit.

**Langkah 2 — Equality + oracle.** Buat dataset deterministik minimal **10.000 object** berisi duplikasi nilai logis. Pisahkan *oracle* dari implementasi object, misalnya kumpulan canonical string atau pasangan `(currency, minorUnits)` di test. Bandingkan jumlah key unik yang diharapkan dengan ukuran `HashSet` dan `HashMap`. Uji reflexivity, symmetry, transitivity, null inequality, dan equal-hash untuk rangkaian sampel yang mencakup seluruh dataset. Gunakan fixed seed agar kegagalan bisa direproduksi.

```java
// Kerangka test, bukan solusi challenge lengkap.

    // TODO: catat canonical oracle independen.
    // TODO: assert kontrak equality dan expected cardinality.

```

**Langkah 3 — Ambush.** Pada fixture/test-only type terpisah, sengaja buat dua object yang `equals`-nya true tetapi hash berbeda. Jalankan test yang sama dan pastikan ia *gagal karena kontrak tersebut*, lalu pulihkan implementasi yang benar. Jangan memasukkan defect ke value object production.

<Reveal title="Contoh bentuk defect yang perlu ditangkap">
Dua instance `BrokenId("acct-7", 1)` dan `BrokenId("acct-7", 2)` boleh dibuat untuk eksperimen. Jika `equals` hanya membandingkan `value`, tetapi `hashCode` mengembalikan `salt`, maka keduanya *equal* dengan hash berbeda. Test yang memeriksa `a.equals(b) ⇒ a.hashCode() == b.hashCode()` harus gagal secara deterministik.
</Reveal>

## Bukti minimum

- Test cases konstruksi invalid/valid yang menunjukkan aturan domain dan semua penolakan.
- Satu run test dengan seed tetap, jumlah object dihasilkan, dan oracle cardinality vs `HashSet`/`HashMap`.
- Assertion kontrak `equals`/`hashCode` serta hasil *red → green* saat defect disengaja disuntik lalu diperbaiki.
- Commit/patch source, test, dan perintah reproducible (`mvn test`).
