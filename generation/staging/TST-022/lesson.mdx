> **Masalah:** bank mungkin menerapkan debit sebelum koneksi timeout. Menganggap gagal lalu mengirim ulang bisa membuat debit duplikat.

**Langkah pertama:** bedakan definitive accepted, known rejection, temporary HTTP condition dan UNKNOWN outcome.

<MentalModel title="Timeout bukan penolakan debit">

- SUCCESS: hanya 200 dengan ACCEPTED, providerReference, amount decimal string dan currency valid; accepted bukan settlement.
- REJECTED: 400 dengan business code INVALID_ACCOUNT yang dikenal.
- RETRYABLE: 429 atau 503 menunjukkan kondisi sementara, bukan izin mengulang POST debit.
- UNKNOWN: timeout, reset, JSON rusak, invalid amount, 200 PENDING atau 400 dengan error yang tidak dikenal.
- Untuk retry debit nyata, lakukan pengecekan status dan pastikan provider idempotency contract terlebih dahulu.

</MentalModel>

<ConceptGraph>

~~~text
POST /bank/debits
      |
  status and payload
      +-- 200 valid ACCEPTED -> SUCCESS (not settled)
      +-- 400 known rejection -> REJECTED
      +-- 429 / 503 ----------> RETRYABLE
      +-- timeout / reset ----> UNKNOWN
      +-- invalid JSON -------> UNKNOWN
                                  |
                            reconcile status
                                  |
                             no blind retry
~~~

</ConceptGraph>

## HTTP fault matrix

| Fault | Mapping | Safe action |
| --- | --- | --- |
| 200 accepted with valid JSON | SUCCESS | Store provider reference |
| 400 INVALID_ACCOUNT | REJECTED | Do not retry |
| 429 rate limit / 503 unavailable | RETRYABLE | Check status before retry |
| Delayed response beyond timeout | UNKNOWN | Query provider status |
| Socket reset after receiving request | UNKNOWN | Query provider status |
| Malformed JSON or unexpected amount type | UNKNOWN | Query provider status |
| Unknown rejection body or PENDING | UNKNOWN | Query provider status |

**Penting:** label RETRYABLE hanya untuk keadaan HTTP sementara. Header Retry-After adalah informasi pacing dan tidak membuktikan debit belum terjadi. Client fixture tidak pernah menjalankan request debit kedua.

## Run real HTTP fault fixture

Dengan Node 24 dari repository root:

~~~sh
node generation/fixtures/TST-022/provider-fault-matrix.mjs
~~~

Expected output:

~~~text
wire-cases=11
success=1;rejected=1;retryable=3;unknown=6
timeout-and-reset=remote-may-have-applied
blind-debit-retries=0
target=local-node-fault-stub-not-wiremock
~~~

Node HTTP server menjalankan sebelas fault di 127.0.0.1 dengan port ephemeral. Pada timeout dan reset, stub mencatat efek debit **sebelum** respons hilang, sedangkan caller tetap UNKNOWN. Semua skenario memiliki satu request; tidak ada retry otomatis.

**Batas bukti:** simulasi memakai Node native, bukan WireMock process. Tidak ada API bank eksternal, database, Spring MVC, JWT, ledger atau pembayaran sungguhan.
