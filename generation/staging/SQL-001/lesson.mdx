## 1. Relational model — tabel, row, dan identity

Dalam relational model, **relation** adalah himpunan tuple berdasarkan atribut. Pada implementasi SQL, sebuah **table** punya kolom bertipe, berisi row, dan query biasa dapat menghasilkan **baris duplikat**. Jangan menyamakan hasil `SELECT` dengan himpunan unik secara otomatis.

Contoh skema awal untuk pembayaran:

| id | merchant_id | amount | status |
| ---: | ---: | ---: | --- |
| 1 | 10 | 100.00 | PAID |
| 2 | 10 | 200.00 | FAILED |
| 3 | 20 | 150.00 | NULL |
| 4 | 20 | 125.50 | PAID |

- **Column** adalah atribut bertipe, misalnya `amount`.
- **Row / tuple** adalah satu kombinasi nilai, misalnya pembayaran `id = 2`.
- **Schema** menetapkan bentuk dan batasan data; nama kolom dan tipe adalah bagian dari kontraknya.
- **Primary key** adalah identitas logis row yang **unik dan non-NULL**, bukan posisi fisik row di disk. PostgreSQL membuat unique B-tree index untuk constraint primary key, tetapi itu **tidak** membuat `SELECT` otomatis terurut.

`PRIMARY KEY (id)` akan menolak dua row dengan `id` sama dan menolak `id = NULL`. Kolom `status` tetap boleh `NULL` bila tidak diberi `NOT NULL`.

<Reveal title="Cek pemahaman — jika dua payment berstatus PAID, apakah SELECT status otomatis unik?">
Tidak. Nilai `PAID` boleh muncul dua kali pada hasil biasa. Constraint primary key berlaku pada `id`, bukan membuat seluruh proyeksi `SELECT status` menjadi unik. Keunikan hasil diminta dengan `DISTINCT` saat memang diperlukan.
</Reveal>

## 2. Cara membaca SELECT: ekspresi bukan selalu tabel

`SELECT` dapat mengevaluasi ekspresi tanpa `FROM`:

```sql
SELECT 2 + 3 AS result;  -- satu row, nilai 5
```

Jika `FROM` digunakan, ekspresi diperhitungkan terhadap baris sumber. `WHERE` memutuskan row mana yang lolos.

```sql
SELECT id, amount
FROM payments
WHERE amount > 150
ORDER BY id;
```

Cara menalar **hasil**, bukan urutan internal eksekusi fisik:

1. Tentukan row dan tipe dari `FROM payments`.
2. Nilai kondisi `amount > 150` untuk setiap row.
3. Pertahankan hanya row dengan kondisi TRUE.
4. Bentuk kolom output `id, amount`.
5. Urutkan sesuai `ORDER BY id`.

Ini kerangka konseptual; optimizer PostgreSQL dapat menjalankan operasi fisik dalam urutan berbeda selama semantiknya terjaga.

### Trace satu query dari baris sumber ke hasil

Gunakan **lima baris** pada `00_setup.sql` di bawah (bukan tabel ilustrasi empat baris di awal). Prediksi dulu sebelum membaca tabel trace:

**Query contoh:** `SELECT id FROM payments WHERE status = 'PAID' ORDER BY id;`

| `id` | `status` | `status = 'PAID'` | Masuk hasil? |
| ---: | --- | --- | --- |
| 1 | PAID | TRUE | Ya |
| 2 | FAILED | FALSE | Tidak |
| 3 | NULL | UNKNOWN | Tidak |
| 4 | PAID | TRUE | Ya |
| 5 | PENDING | FALSE | Tidak |

Output berurutan adalah `1, 4`. Kalau kamu mengira `id = 3` ikut karena UNKNOWN bukan FALSE, modelnya keliru: **WHERE hanya mengambil TRUE**. Untuk memprediksi query lain, pisahkan pertanyaan *nilai kondisi per row* dan *urutan hasil*.

## 3. NULL dan three-valued logic (3VL)

`NULL` berarti **tidak ada nilai yang diketahui** pada posisi tersebut, bukan `0`, bukan string kosong, bukan `FALSE`. SQL memiliki tiga nilai logika: **TRUE, FALSE, UNKNOWN** (direpresentasikan sebagai `NULL` pada hasil ekspresi boolean).

Operator perbandingan biasa seperti `=`, `<>`, `<`, atau `>` tidak bisa menyimpulkan TRUE/FALSE jika salah satu operand `NULL`.

```sql
SELECT 9 = NULL;       -- NULL / UNKNOWN
SELECT 9 <> NULL;      -- NULL / UNKNOWN
SELECT NULL = NULL;    -- NULL / UNKNOWN
```

Karena dua nilai yang tidak diketahui tidak otomatis sama atau berbeda, **jangan** gunakan `= NULL` atau `<> NULL` untuk memeriksa ketiadaan nilai.

| Kebutuhan | Operator yang tepat |
| --- | --- |
| Apakah nilainya NULL? | `IS NULL` |
| Apakah nilainya bukan NULL? | `IS NOT NULL` |
| Equality yang menganggap dua NULL setara | `IS NOT DISTINCT FROM` |
| Inequality yang menghasilkan TRUE/FALSE juga untuk NULL | `IS DISTINCT FROM` |

```sql
SELECT NULL IS NULL;                       -- TRUE
SELECT NULL IS NOT DISTINCT FROM NULL;     -- TRUE
SELECT 9 IS DISTINCT FROM NULL;            -- TRUE
```

### Logika AND, OR, dan NOT

| A | B | A AND B | A OR B |
| --- | --- | --- | --- |
| TRUE | TRUE | TRUE | TRUE |
| TRUE | FALSE | FALSE | TRUE |
| TRUE | UNKNOWN | UNKNOWN | TRUE |
| FALSE | FALSE | FALSE | FALSE |
| FALSE | UNKNOWN | FALSE | UNKNOWN |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

`NOT TRUE` adalah FALSE, `NOT FALSE` adalah TRUE, dan `NOT UNKNOWN` tetap UNKNOWN.

**Pola penalaran:** `FALSE AND x` selalu FALSE karena syarat gabungan pasti gagal; `TRUE OR x` selalu TRUE karena satu sisi sudah cukup. Sebaliknya, `TRUE AND UNKNOWN` dan `FALSE OR UNKNOWN` masih bergantung pada informasi yang tidak diketahui.

<Reveal title="Mengapa FALSE AND UNKNOWN bukan UNKNOWN?">
`AND` hanya TRUE bila **kedua** operand TRUE. Begitu satu sisi FALSE, hasilnya pasti FALSE terlepas dari sisi lainnya. Ini evaluasi nilai logika; jangan mengasumsikan PostgreSQL selalu mengeksekusi operand kiri lebih dahulu.
</Reveal>

**Pembedaan yang sering menipu:** kontrak `NULL` adalah bagian dari *data*, sedangkan tampilan `[NULL]` hanyalah konfigurasi `psql`. Mengubah `\pset null` tidak mengubah hasil query, tipe kolom, atau cara `WHERE` bekerja.
## 4. WHERE mempertahankan TRUE, bukan semua yang tidak FALSE

Misalkan `status` pada payment `id=3` adalah `NULL`.

```sql
SELECT id, status
FROM payments
WHERE status <> 'PAID'
ORDER BY id;
```

Untuk row dengan status FAILED atau PENDING, predikat TRUE. Untuk status PAID, predikat FALSE. Untuk status NULL, predikat UNKNOWN sehingga **row tidak lolos**.

| Row status | `status <> 'PAID'` | Lolos `WHERE`? |
| --- | --- | --- |
| FAILED | TRUE | Ya |
| PAID | FALSE | Tidak |
| NULL | UNKNOWN | Tidak |

Jika kebutuhan bisnisnya “semua payment yang bukan PAID **termasuk yang statusnya belum diketahui**”, kondisi harus ditulis berbeda:

```sql
WHERE status IS DISTINCT FROM 'PAID'
```

Perbedaan penting: **filter SQL bukan JavaScript truthy/falsy**; ia menerima hanya TRUE.

### Jebakan NOT IN

`x NOT IN (1, 2, NULL)` secara konseptual serupa dengan:

```text
x <> 1 AND x <> 2 AND x <> NULL
```

Jika ada match dengan 1 atau 2, hasilnya FALSE. Jika tidak ada match tetapi ada NULL di daftar, hasilnya UNKNOWN, bukan TRUE.

```sql
SELECT 7 NOT IN (1, 2, NULL);  -- UNKNOWN
SELECT 2 NOT IN (1, 2, NULL);  -- FALSE
```

Ini penting saat mengecualikan daftar payment yang memiliki kemungkinan `NULL`. Untuk daftar/subquery nullable, jangan memakai `NOT IN` begitu saja tanpa memahami semantik NULL. `NOT EXISTS` dengan relasi yang tepat sering lebih aman untuk anti-match; detail joins dan subqueries akan dipelajari pada `SQL-002`.

## 5. Duplicate rows, DISTINCT, dan identitas

Perhatikan dua payment memiliki status PAID. Query:

```sql
SELECT status
FROM payments
WHERE status = 'PAID';
```

menghasilkan dua row dengan nilai PAID. SQL memakai semantik *bag/multiset* untuk banyak operasi hasil query: **duplikat bisa tetap ada**.

```sql
SELECT DISTINCT status
FROM payments;
```

`DISTINCT` menghapus baris hasil yang sama untuk kolom yang diproyeksikan, bukan menghapus row sumber. Untuk tujuan deduplikasi hasil, nilai NULL yang sama diperlakukan sebagai duplikat; tetapi `NULL = NULL` tetap UNKNOWN dalam perbandingan biasa. Ini dua konteks semantik yang berbeda.

**Jangan menganggap `DISTINCT` mengurutkan.** Jika perlu urutan hasil, pakai `ORDER BY` secara eksplisit.

## 6. PostgreSQL data types — makna menentukan tipe

| Tipe | Kapan dipakai | Risiko bila salah |
| --- | --- | --- |
| `integer` / `bigint` | Hitungan dan identifier bilangan bulat | Range integer terbatas |
| `numeric(18,2)` | Nilai uang desimal yang harus exact pada skala 2 | Presisi/scale perlu ditentukan sesuai domain |
| `text` | Status atau data teks | Teks bukan angka untuk operasi aritmetika |
| `boolean` | Flag benar/salah; nullable menambah UNKNOWN | NULL tidak sama dengan FALSE |
| `date` | Tanggal kalender | Bukan instant waktu |
| `timestamptz` | Timestamp instant (mis. event pembayaran) | Interpretasi/tampilan bergantung zona waktu sesi |
| `uuid` | Identifier UUID | Berbeda dari integer sequence |

Untuk pembayaran, nilai `100.10` lebih tepat disimpan dengan `numeric` ketika exact decimal diperlukan, bukan `double precision`. `timestamp without time zone` menyimpan tanggal-jam tanpa informasi zona, sedangkan `timestamptz` merepresentasikan instant; PostgreSQL tidak menyimpan label zona aslinya di kolom `timestamptz`.

**Casting:** PostgreSQL dapat menginfer tipe literal `'10'` yang awalnya bertipe `unknown` ketika operator memberi konteks:

```sql
SELECT '10' + 2;         -- 12; literal unknown diresolusikan sebagai integer
SELECT '10'::integer + 2; -- 12; cast eksplisit
```

Jangan generalisasikan menjadi “semua kolom text bisa ditambah integer”; kolom `text` yang sudah bertipe berbeda dari literal `'10'` yang belum ditentukan tipenya. Cast eksplisit saat kontrak mengharuskannya, dan pastikan input valid.

## 7. ORDER BY, LIMIT, dan determinism

Tanpa `ORDER BY`, tidak ada jaminan urutan row, bahkan jika hasil sering terlihat konsisten pada database kecil.

```sql
SELECT id FROM payments LIMIT 2;  -- tidak menjanjikan dua id tertentu
```

Jika maksudnya “dua pembayaran paling awal”, butuh aturan urutan yang lengkap:

```sql
SELECT id
FROM payments
ORDER BY created_at, id
LIMIT 2;
```

`created_at` saja bisa memiliki nilai sama pada beberapa row. Tambahan `id` (unik) adalah *tie-breaker* sehingga urutan total jelas. Saat menyortir nullable column, tetapkan posisi NULL bila dibutuhkan: `ORDER BY status ASC NULLS LAST`.

<MentalModel title="Benar bukan hanya isi row, tetapi juga kontrak ordering">
Query yang tampaknya selalu mengembalikan row yang sama belum tentu deterministik. Jika memilih “top N”, memakai pagination, atau membandingkan hasil untuk test, `ORDER BY` dengan tie-breaker unik adalah bagian dari correctness.
</MentalModel>

```sql
DROP TABLE IF EXISTS payments;

  id bigint PRIMARY KEY,

  (5, 30, 500.00, 'PENDING', '2026-10-10 09:02:00+00');
COMMIT;
```

```bash

psql -X -v ON_ERROR_STOP=1 -d cs101_sql001
```

Di dalam sesi `psql`, jalankan `\pset null '[NULL]'` agar output NULL tidak terlihat seperti string kosong. Lalu coba:

```sql
SELECT id, status
FROM payments
```


## 10. SQL Semantics Minefield — 20 prediksi sebelum eksekusi

**Jangan jalankan kasus berikut sebelum prediksinya ditulis.** Dataset adalah lima row dari `00_setup.sql` pada tahap Pahami. Tulis 20 prediksi terpisah tanpa mencari jawaban. Untuk setiap kasus, catat: `ID | predicted result (termasuk row count dan order jika dijamin) | reasoning`. Untuk setiap kelompok lima soal, kunci dulu kelima prediksi sebelum mengeksekusinya. Lalu simpan `actual result | correct? | correction` tanpa mengubah prediksi yang sudah dikunci.

**Cara mengerjakannya tanpa ceremony:** buat satu file prediksi berisi 20 baris dengan format `ID | prediksi | alasan`. Kerjakan dalam empat kelompok lima kasus. Untuk setiap kelompok, tulis prediksi **sebelum** menjalankan query kelompok tersebut, lalu cek dan koreksi. Prediksi awal tidak boleh diedit. Tidak perlu timer, laporan panjang, atau formulir tambahan.

**Kontrak prediksi:** untuk scalar, tulis nilai beserta `NULL` jika UNKNOWN; untuk rowset, tulis *jumlah*, *nilai yang muncul*, dan *urutan* hanya jika SQL menjaminnya. `ERROR` berbeda dari hasil `NULL`. Untuk query tanpa ordering, tulis batas jaminan yang benar, bukan menebak urutan fisik.

Kasus 1–5: scalar, ordinary comparisons, dan three-valued logic.

```sql
-- 01: SELECT tanpa FROM
SELECT 42 AS result;
-- 02: equality dengan NULL
SELECT 12 = NULL AS result;
-- 03: AND dengan UNKNOWN
SELECT FALSE AND (3 > NULL) AS result;
-- 04: OR dengan UNKNOWN
SELECT TRUE OR (3 > NULL) AS result;
-- 05: NOT dengan UNKNOWN
SELECT NOT (3 > NULL) AS result;
```

Kasus 6–10: null-safe equality dan pemilihan row. Gunakan lima row dari `00_setup.sql`.

```sql
-- 06
SELECT NULL IS NOT DISTINCT FROM NULL AS result;
-- 07
SELECT 12 IS DISTINCT FROM NULL AS result;
-- 08
SELECT id FROM payments WHERE status = 'FAILED' ORDER BY id;
-- 09
SELECT id FROM payments WHERE status <> 'FAILED' ORDER BY id;
-- 10
SELECT id FROM payments WHERE status IS DISTINCT FROM 'FAILED' ORDER BY id;
```

Kasus 11–15: `NOT IN`, baris duplikat, dan `DISTINCT`.

```sql
-- 11
SELECT 3 NOT IN (1, 2, NULL) AS result;
-- 12
SELECT 2 NOT IN (1, 2, NULL) AS result;
-- 13
SELECT status FROM payments WHERE status = 'PAID' ORDER BY id;
-- 14
SELECT DISTINCT status FROM payments ORDER BY status NULLS LAST;
-- 15
SELECT DISTINCT merchant_id FROM payments ORDER BY merchant_id;
```

Kasus 16–20: numeric, sorting, `LIMIT`, dan literal type inference.

```sql
-- 16: dua kolom dengan urutan yang eksplisit
SELECT id, amount FROM payments WHERE amount >= 150 ORDER BY amount DESC, id;
-- 17: aritmetika desimal exact
SELECT 0.1::numeric + 0.2::numeric AS result;
-- 18: tanpa ORDER BY
SELECT id FROM payments LIMIT 2;
-- 19: created_at bisa sama; id menjadi tie-breaker
SELECT id FROM payments ORDER BY created_at, id LIMIT 2;
-- 20: unknown literal dan operator resolution
SELECT '10' + 2 AS result;
```
**Khusus kasus 18:** jawaban yang benar bukan menebak dua ID. Jelaskan apa yang **dijamin** oleh query dan apa yang **tidak dijamin**; assertion juga harus memeriksa kontrak itu, bukan mengunci urutan kebetulan.

### Template assertion yang benar-benar gagal saat prediksi salah

`psql` bukan runner test otomatis hanya karena query berhasil dieksekusi. Untuk membuat suatu pemeriksaan benar-benar *fail*, gunakan `DO` dengan `RAISE EXCEPTION`, kemudian jalankan `psql -v ON_ERROR_STOP=1`. Dua contoh berikut **bukan jawaban untuk 20 kasus**:

```sql
-- Contoh A: verifikasi scalar nullable dari ekspresi lain
DO $qa$
BEGIN
  IF NOT ((NULL::integer = 99) IS UNKNOWN) THEN
    RAISE EXCEPTION 'Expected UNKNOWN for nullable comparison';
  END IF;
END
$qa$;

-- Contoh B: verifikasi himpunan ID dengan ordering eksplisit
DO $qa$
DECLARE observed bigint[];
BEGIN
  SELECT array_agg(id ORDER BY id) INTO observed
  FROM payments WHERE merchant_id = 20;
  IF observed IS DISTINCT FROM ARRAY[3, 4]::bigint[] THEN
    RAISE EXCEPTION 'Merchant 20 IDs mismatch: %', observed;
  END IF;
END
$qa$;
```

Untuk kasusmu, pilih satu pemeriksaan per prediksi: **scalar** (`IS [NOT] DISTINCT FROM` bila NULL mungkin muncul), **cardinality**, atau **ordered rowset**. Jangan menambahkan `ORDER BY` diam-diam ke query yang sengaja menguji nondeterminism: pisahkan *query yang diuji* dari *cara assertion membandingkan baris*. Assertion untuk query tanpa ORDER BY tidak boleh mengunci urutan yang bukan bagian dari kontraknya.
Jika klaim `18/20` belum terbukti, **jangan** tandai unit lulus. Review reasoning yang salah, siapkan kasus baru dengan semantik serupa tetapi input berbeda, lalu uji ulang tanpa melihat hasil terlebih dahulu.
