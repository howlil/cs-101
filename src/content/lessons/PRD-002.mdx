> **Target:** implementasikan /live dan /ready pada Spring Boot sehingga startup lambat, database down, recovery, dan graceful drain tidak menyebabkan dependency-driven liveness restart loop.

**Mulai:** tulis status /live dan /ready ketika proses responsif tetapi database yang wajib untuk transfer tidak tersedia.

<MentalModel title="Process alive ≠ service ready">

- **Liveness:** kesehatan proses dan kemungkinan restart jika tidak bisa membuat kemajuan.
- **Readiness:** penerimaan trafik normal Kubernetes Service saat instance sanggup bekerja.
- **Startup probe:** memberi ruang untuk cold start, menunda liveness/readiness probes sampai startup berhasil.
- **Graceful shutdown:** berhenti menerima pekerjaan baru sambil menyelesaikan in-flight request dalam batas waktu.

**Penting:** status /live 200 bukan bukti sebuah operasi transfer aman, sah, idempotent, atau tercatat di ledger.

</MentalModel>

## Contoh Spring Boot Actuator

Tambahkan dependency `spring-boot-starter-actuator`. Spring Boot memiliki health groups `/actuator/health/liveness` dan `/actuator/health/readiness`. Ekspos alias ini pada **port HTTP utama**:

```properties
management.endpoint.health.probes.enabled=true
management.endpoint.health.group.liveness.additional-path=server:/live
management.endpoint.health.group.readiness.additional-path=server:/ready
management.endpoint.health.show-details=never
```

Indikator eksternal **tidak otomatis** menjadi bagian readiness. Jika ledger DB wajib agar transfer dapat dilayani, implementasikan health indicator `transferDbHealthIndicator` dengan pemeriksaan berbiaya rendah dan timeout terbatasi, kemudian sertakan dalam readiness saja:

```properties
management.endpoint.health.group.readiness.include=readinessState,transferDb
```

Jangan memasukkan database ke liveness. Shared DB down bisa membuat semua replica menjadi unready: apakah itu benar harus diputuskan berdasarkan kebutuhan service dan risiko semua endpoint hilang.

## Kubernetes probe policy (contoh, bukan bukti cluster)

```yaml
startupProbe:
  httpGet: { path: /live, port: 8080 }
  periodSeconds: 5
  failureThreshold: 24
livenessProbe:
  httpGet: { path: /live, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2
```

Contoh startup budget sekitar `5 × 24 = 120` detik probe failures, bukan timing guarantee. Jika HTTP server sudah aktif tetapi mandatory warmup belum selesai, `/live` bisa 200 sementara `/ready` masih 503. Atur threshold berdasarkan startup yang benar-benar diukur.

## Prove: Health Contract pada Spring Boot

<LearningSegments stage="evidence" segments={lessonSegments} />

Verifikasi pada aplikasi Spring Boot dan Kubernetes disposable, bukan cluster produksi. Uji startup lambat, DB down, recovery dan graceful SIGTERM; lihat HTTP probe dan kondisi Service endpoints:

```sh
curl -i http://127.0.0.1:8080/live
curl -i http://127.0.0.1:8080/ready
kubectl get pods -w
kubectl get endpointslices
```

Readiness 503 membatasi trafik melalui Service yang dikonfigurasi; akses langsung ke Pod IP memerlukan perlindungan tambahan. Graceful shutdown Spring Boot harus menggunakan grace phase timeout yang cukup dan diintegrasikan dengan termination grace Kubernetes.
