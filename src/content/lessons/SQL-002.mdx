> Sebelum menulis join, tentukan dulu **satu row output merepresentasikan apa**. Itu cara paling cepat mencegah duplicate amplification dan query yang benar secara syntax tetapi salah secara bisnis.

## Setelah materi ini, lo harus bisa

- memilih `INNER JOIN` vs `LEFT JOIN` berdasarkan pertanyaan;
- memprediksi cardinality sebelum query dijalankan;
- menjelaskan kenapa join dapat menggandakan row;
- memakai `EXISTS` / `NOT EXISTS` untuk pertanyaan keberadaan;
- memecah reasoning dengan CTE tanpa memindahkan business logic ke aplikasi;
- membedakan `UNION` dan `UNION ALL`;
- menyelesaikan pertanyaan multi-table dalam satu SQL statement.

<MentalModel title="Grain dulu, baru join">
Tentukan grain hasil: **satu row output = apa?** Setelah itu, untuk setiap join tanyakan berapa row pasangan yang mungkin muncul untuk satu row kiri. Join tidak “menempelkan kolom”; join membentuk pasangan row yang memenuhi kondisi. Kalau satu order cocok dengan tiga payment rows, order itu muncul tiga kali sebelum tahap query berikutnya.

## INNER JOIN dan LEFT JOIN

`INNER JOIN` hanya mempertahankan pasangan yang match.

```sql
SELECT o.id, p.id AS payment_id
FROM orders o
JOIN payments p ON p.order_id = o.id;
```

`LEFT JOIN` mempertahankan semua row kiri; bila tidak ada match, column dari sisi kanan menjadi null.

```sql
SELECT o.id, p.id AS payment_id
FROM orders o
LEFT JOIN payments p ON p.order_id = o.id;
```

Jangan memilih LEFT JOIN hanya karena terasa “lebih aman”. Pilih berdasarkan pertanyaan.

## Duplicate amplification adalah masalah grain

Misalnya:

```text
orders
o1

payments
p1 → o1
p2 → o1

refunds
r1 → p1
r2 → p1
```

Join `orders → payments → refunds` tidak menghasilkan “satu row per order”. Ia menghasilkan pasangan sesuai relationship. Kalau lalu `SUM(order.amount)` dilakukan tanpa memperbaiki grain, amount order bisa terhitung berulang.

Sebelum query:

1. tulis grain setiap tabel;
2. tulis multiplicity relationship;
3. prediksi jumlah row intermediate;
4. baru pilih join/aggregation.

## EXISTS untuk pertanyaan “apakah ada?”

Kalau pertanyaannya:

> merchant mana yang punya minimal satu payment gagal?

lo tidak membutuhkan semua matching payment rows.

```sql
SELECT m.id
FROM merchants m
WHERE EXISTS (
  SELECT 1
  FROM payments p
  WHERE p.merchant_id = m.id
    AND p.status = 'failed'
);
```

`EXISTS` bernilai true kalau subquery menghasilkan setidaknya satu row. Output list subquery biasanya tidak penting.

Untuk “tidak punya”:

```sql
SELECT m.id
FROM merchants m
WHERE NOT EXISTS (
  SELECT 1
  FROM payments p
  WHERE p.merchant_id = m.id
);
```

Ini menjaga grain outer query: satu merchant tetap maksimal satu row.

## Correlated subquery

Subquery disebut correlated ketika merujuk value dari outer row:

```sql
SELECT o.id
FROM orders o
WHERE EXISTS (
  SELECT 1
  FROM payments p
  WHERE p.order_id = o.id
);
```

Mental modelnya: untuk current outer row, cek apakah condition subquery memiliki row yang memenuhi. Jangan otomatis menganggap correlated subquery lambat; ukur plan nanti. Di materi ini fokus dulu ke semantics.

## CTE untuk memberi nama tahap reasoning

`WITH` bisa membuat query multi-stage lebih mudah diverifikasi.

```sql
WITH paid_orders AS (
  SELECT DISTINCT order_id
  FROM payments
  WHERE status = 'paid'
)
SELECT o.id
FROM orders o
JOIN paid_orders p ON p.order_id = o.id;
```

CTE bukan alasan untuk memecah setiap dua baris SQL. Pakai ketika nama intermediate result membantu menjelaskan grain atau aturan.

## Self join

Self join memakai tabel yang sama dalam dua role berbeda.

Contoh struktur referral:

```sql
SELECT child.id, parent.id AS referrer_id
FROM customers child
LEFT JOIN customers parent
  ON parent.id = child.referred_by;
```

Alias bukan kosmetik: ia menyatakan role dari setiap instance tabel.

## UNION vs UNION ALL

`UNION` menggabungkan dua compatible result set dan menghapus duplicate rows.

`UNION ALL` mempertahankan semua rows, termasuk duplikat.

```sql
SELECT merchant_id FROM card_payments
UNION ALL
SELECT merchant_id FROM bank_payments;
```

Kalau duplikat punya arti bisnis atau tidak perlu dihapus, jangan membayar semantic/cost dedup tanpa alasan.

## Jangan pindahkan query logic ke application loop

Kalau pertanyaan adalah:

> order mana yang punya payment sukses tetapi tidak pernah direfund?

lebih baik express relation-nya di SQL:

```sql
SELECT o.id
FROM orders o
WHERE EXISTS (
  SELECT 1
  FROM payments p
  WHERE p.order_id = o.id
    AND p.status = 'paid'
)
AND NOT EXISTS (
  SELECT 1
  FROM refunds r
  JOIN payments p ON p.id = r.payment_id
  WHERE p.order_id = o.id
);
```

Bukan fetch semua tabel lalu loop/filter di Java/JavaScript.

## Checklist sebelum execute

Untuk setiap query multi-table, tulis:

```text
Output grain:
Expected row count / range:
Relationship:
Potential amplification:
Why JOIN / EXISTS / CTE:
```

Kalau lo belum bisa mengisi ini, query-nya belum siap dijalankan.

<Reveal title="Kenapa DISTINCT bukan obat untuk join yang salah?">
`DISTINCT` dapat menghapus duplicate output rows, tetapi tidak memperbaiki model relationship yang salah. Ia juga bisa menyembunyikan amplification sebelum aggregation. Perbaiki grain dan join condition lebih dulu.
</Reveal>
