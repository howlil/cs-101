## Row bukan identitas

Satu row adalah satu tuple nilai. Kalau aplikasi perlu menunjuk satu row secara stabil, schema harus punya identitas yang jelas.

Di PostgreSQL, `PRIMARY KEY` berarti nilai key harus unik dan tidak boleh `NULL`. Primary key juga memberi metadata yang bisa dipakai relasi lain sebagai target foreign key.

```sql
CREATE TABLE payment (
  id bigint PRIMARY KEY,
  merchant_id bigint NOT NULL,
  amount numeric(18,2) NOT NULL,
  status text NOT NULL
);
```

Jangan menganggap posisi fisik row sebagai identitas. Query planner bebas memilih cara membaca tabel.

## NULL berarti “tidak diketahui”

`NULL` bukan angka nol, string kosong, atau sentinel biasa.

Perbandingan biasa dengan `NULL` menghasilkan `NULL`/unknown:

```sql
SELECT 7 = NULL;       -- NULL
SELECT 7 <> NULL;      -- NULL
SELECT NULL = NULL;    -- NULL
```

Karena itu cek `NULL` memakai:

```sql
value IS NULL
value IS NOT NULL
```

Untuk perbandingan yang sengaja memperlakukan `NULL` sebagai nilai yang bisa dibandingkan, PostgreSQL menyediakan `IS DISTINCT FROM` dan `IS NOT DISTINCT FROM`.

<Reveal title="Kenapa WHERE x <> NULL tidak mengembalikan row?">
`x <> NULL` menghasilkan unknown. `WHERE` hanya mempertahankan kondisi yang bernilai true; false dan unknown sama-sama tidak lolos filter.
</Reveal>

## Jebakan NOT IN

Baca:

```sql
x NOT IN (1, 2, NULL)
```

secara mental sebagai rangkaian:

```text
x <> 1
AND x <> 2
AND x <> NULL
```

Kalau `x` bukan 1 atau 2, bagian terakhir tetap unknown. Hasil keseluruhan bisa menjadi unknown, bukan true.

Contoh:

```sql
SELECT 3 NOT IN (1, 2, NULL); -- NULL
```

Ini alasan `NOT IN` sering berbahaya bila sumber nilai bisa mengandung `NULL`. Sebelum memilih operator, pahami contract datanya.

## Duplikat dan DISTINCT

SQL tidak otomatis menjadikan semua hasil sebagai set unik.

```sql
SELECT status FROM payment;
```

bisa menghasilkan status yang sama berkali-kali. `DISTINCT` menghapus duplicate result rows:

```sql
SELECT DISTINCT status
FROM payment;
```

Tetapi `DISTINCT` **tidak berarti hasil menjadi terurut**.

## Tipe data adalah bagian dari contract

Pilih tipe berdasarkan makna data, bukan sekadar “bisa menyimpan nilainya”.

- `integer` / `bigint` untuk bilangan bulat;
- `numeric(p,s)` untuk angka desimal exact dengan precision yang dipilih;
- `text` untuk string;
- `boolean` untuk true/false, dengan `NULL` sebagai unknown bila column nullable;
- `date` untuk tanggal kalender;
- `timestamp with time zone` / `timestamptz` untuk instant yang perlu semantics zona waktu;
- `uuid` untuk identifier UUID.

Implicit cast bisa membuat query tampak bekerja tetapi menyembunyikan asumsi tipe. Di latihan, biasakan tahu tipe operand sebelum memprediksi hasil.

## ORDER BY adalah bagian dari correctness

Tanpa `ORDER BY`, SQL tidak menjanjikan urutan hasil.

Query ini tidak punya “tiga payment pertama” yang stabil:

```sql
SELECT id
FROM payment
LIMIT 3;
```

Kalau kebutuhan bisnis mengharuskan urutan tertentu:

```sql
SELECT id
FROM payment
ORDER BY id
LIMIT 3;
```

Kalau kolom ordering tidak unik, tambahkan tie-breaker sampai urutannya cukup unik:

```sql
ORDER BY created_at, id
```

Maka determinism bukan kosmetik UI. Ia bagian dari contract query.

## Workflow minimum di psql

Bangun latihan tanpa ORM:

```sql
CREATE TABLE sample (
  id bigint PRIMARY KEY,
  value integer,
  label text
);

INSERT INTO sample (id, value, label) VALUES
  (1, 10, 'a'),
  (2, NULL, 'b'),
  (3, 10, 'a');

SELECT id, value
FROM sample
WHERE value <> 10
ORDER BY id;
```

Sebelum query terakhir dijalankan, prediksi row mana yang lolos dan jelaskan kenapa.

## Wrong models yang harus dibuang

- “`NULL` sama dengan kosong.”
- “Kondisi SQL selalu true atau false.”
- “`NOT IN` aman selama value yang dicari tidak null.”
- “`DISTINCT` juga mengurutkan.”
- “Kalau query kemarin keluar berurutan, berarti urutannya stabil.”
- “Primary key cuma index performa.”

## Latihan prediksi

Prediksi hasil sebelum menjalankan:

```sql
SELECT NULL = NULL;
SELECT 5 <> NULL;
SELECT 3 NOT IN (1, 2, NULL);
SELECT TRUE AND NULL;
SELECT FALSE AND NULL;
SELECT DISTINCT x FROM (VALUES (2), (1), (2)) AS t(x);
SELECT x FROM (VALUES (2), (1), (2)) AS t(x) LIMIT 1;
```

Untuk dua query terakhir, jangan menebak order yang tidak dijanjikan.
