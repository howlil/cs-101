<LessonStage stage="understand">

> Dari transaksi berulang, buat laporan urutan pertama, saldo per akun, dan **Top-K akun** tanpa menyortir seluruh akun. Struktur data menentukan apakah hasil benar dan bagaimana biaya meningkat ketika data membesar.

## Outcome

- Pilih `List`, `Set`, `Map`, `Queue`, atau `Deque` dari operasi yang dominan, bukan kebiasaan.
- Prediksi Big-O serta asumsi biaya untuk setidaknya **9 dari 10 skenario backend**.
- Pahami generics, tipe berbatas, `Comparator`, perilaku hash dan urutan iterasi.
- Bangun Top-K menggunakan **heap ukuran maksimal K**, validasi terhadap full-sort oracle pada **100 dataset ber-seed**, dan hilangkan raw/unchecked warnings.

## Prasyarat

[JAV-002 — OOP + object contracts](/learn/JAV-002) wajib dipahami: `TransactionId` dan `AccountId` adalah value objects yang immutable dan patuh `equals/hashCode`. Inilah dasar deduplikasi dan `HashMap` key yang benar.

## 1. Kontrak koleksi dan pilihan implementasi

| Kebutuhan | Pilihan | Operasi dominan dan biaya |
| --- | --- | --- |
| Akses index, tambah di ujung | `ArrayList<E>` | get(index) O(1); append amortized O(1); insert awal O(n) |
| Unik tanpa urutan | `HashSet<E>` | add/contains expected O(1), **bukan** ordered |
| Unik **dengan first-seen order** | `LinkedHashSet<E>` | keunikan hash + insertion-order iteration; extra memory |
| Lookup/update saldo per ID | `HashMap<K,V>` | get/put expected O(1) dengan hash tersebar baik |
| FIFO sederhana dari kedua ujung | `ArrayDeque<E>` | add/remove pada ujung amortized O(1) |
| Ambil kandidat ranking terburuk/terbaik | `PriorityQueue<E>` | offer/poll O(log m), peek O(1), iterator **tak terurut** |

Biaya `HashMap` atau `HashSet` itu **expected**, tidak otomatis worst-case O(1); collision, resize, dan key buruk mengubah kerja aktual. `LinkedHashSet` menjaga *insertion order* dan menambah elemen yang sudah ada tidak memindahkan posisi first-seen. `Queue` tidak berarti selalu FIFO: priority queue memilih head menurut comparator, sedangkan `Deque` mendukung dua ujung. Jangan memakai `LinkedList` hanya karena terasa mudah untuk insert; mencari indeks di linked list tetap memerlukan traversal.

## 2. Generics = kontrak yang diperiksa compiler

~~~java
Set<TransactionId> seen = new HashSet<>();
Map<AccountId, java.math.BigInteger> balance = new HashMap<>();
List<AccountId> ordered = new ArrayList<>();
~~~

Generic type parameter menghindarkan cast manual dari `Object`. Dalam API yang hanya *membaca* subtype, wildcard semisal `List<? extends Number>` dapat menerima `List<Integer>`; ia tidak berarti aman menambahkan sembarang `Number`. Untuk algoritma yang membutuhkan operasi tertentu, type parameter berbatas seperti `<T extends Comparable<? super T>>` menyatakan kemampuan tipe, bukan casting runtime.

<Reveal title="Kenapa List<Integer> bukan List<Number>?">
Jika `List<Integer>` boleh diperlakukan sebagai `List<Number>`, kode lain dapat menambahkan `Double` ke dalamnya. Java generics bersifat invariant untuk mencegah pelanggaran itu. Upper-bounded wildcard dipakai pada interface pembaca ketika benar-benar diperlukan.
</Reveal>

## 3. Urutan first-seen berbeda dari sorting

Input ID `[tx-2, tx-1, tx-2, tx-3, tx-1]` menghasilkan `[tx-2, tx-1, tx-3]`. `HashSet` cukup untuk keunikan, tetapi **tidak** menjamin iterasi sesuai arrival order. `LinkedHashSet<TransactionId>` menjaga keduanya.

~~~java
Set<String> firstSeen = new LinkedHashSet<>();
for (String id : List.of("tx-2", "tx-1", "tx-2", "tx-3", "tx-1")) {
    firstSeen.add(id);
}
System.out.println(firstSeen); // [tx-2, tx-1, tx-3]
~~~

Untuk satu-pass ingestion, gunakan `seen.add(id)` sebagai keputusan pertama sebelum memperbarui saldo. Satu transaksi duplikat tidak boleh memengaruhi agregasi kedua kalinya. Ingat: jumlah account tidak sama dengan jumlah transaksi unik.

## 4. Comparator adalah spesifikasi hasil, bukan dekorasi

Kontrak report:

1. `absolute(balance)` lebih besar didahulukan.
2. Saat absolut saldo sama, `AccountId` lexicographic ascending.
3. AccountId unik menghasilkan total order yang deterministik.

Jika memakai `BigInteger` untuk saldo dalam minor units, lakukan `abs()` langsung; jangan `Math.abs(long)` sembarangan karena `Long.MIN_VALUE` tak memiliki nilai positif yang muat dalam `long`. Dalam heap bounded-K, head harus kandidat **terburuk**: absolute saldo paling kecil, dan saat seri ID lexicographic paling besar. Kandidat lebih baik menggantikan head. Untuk output, *sort hanya K finalist* menggunakan urutan laporan descending tadi.

<ConceptGraph>
<pre>{`heap size <= k
incoming account balance
     |
     +--> size < k? --> offer
     |
     +--> strictly better than heap.peek()? --> poll + offer
     |
     +--> otherwise skip
end: sort only k finalists

Top-K objective: O(a log k + k log k)
Full sort oracle: O(a log a)
(a = distinct accounts; k = min(requestedK, a))`}</pre>
</ConceptGraph>

`PriorityQueue.iterator()` **bukan** sorted traversal; `peek()` hanya menjamin head. Gunakan comparator yang sama semantiknya di heap dan oracle, tetapi terbalik sesuai posisi kandidat terburuk pada heap. Uji juga `k = 0`, `k > a`, negatif/positif dengan absolut sama, duplikasi transaksi, dan tie account ID.

## 5. Dua fase, tetapi hanya satu pass atas transaksi

**Ingest:** scan `n` event tepat sekali, deduplicate by `TransactionId`, append first-seen ID dan update `Map<AccountId, BigInteger>`. Dengan hash yang terdistribusi baik, expected time **O(n)**; space **O(u + a)** untuk `u` unique IDs dan `a` accounts.

**Report:** scan `a` saldo akun (bukan scan ulang transaksi), pertahankan heap ukuran `k`, lalu sort `k` hasil saja. Time **O(a log k + k log k)** untuk `k >= 2`, dengan kasus `k <= 1` ditangani terpisah; auxiliary heap **O(k)**. Total expected **O(n + a log k + k log k)**, storage **O(u + a + k)**. Full-sort hanya dijalankan pada *oracle test*, tidak pada implementasi produksi.

## Sepuluh prediksi struktur

Sebelum menulis kode, jawab **struktur + Big-O**: (1) index read pada event array; (2) repeated insert awal pada ArrayList; (3) dedup unordered ID; (4) dedup ordered ID; (5) lookup saldo per account; (6) FIFO queue; (7) double-ended queue; (8) bounded Top-K; (9) cek membership terhadap HashSet; (10) mengurutkan semua akun untuk full report. Target minimal 9 jawaban benar.

<Reveal title="Periksa 10 prediksi">
1. ArrayList get O(1).
2. ArrayList insert awal O(n).
3. HashSet add expected O(1).
4. LinkedHashSet add expected O(1), iteration ordered.
5. HashMap get/put expected O(1).
6. ArrayDeque offerLast/pollFirst amortized O(1).
7. ArrayDeque kedua ujung amortized O(1).
8. PriorityQueue bounded k, tiap offer/poll O(log k).
9. HashSet contains expected O(1).
10. Full sort seluruh a akun O(a log a); ini **oracle**, bukan implementasi Top-K.
</Reveal>

**Tahap C — Top-K & oracle.** Buat Comparator deterministik: terbesar menurut nilai absolut saldo, kemudian ID terkecil lexicographic. Implementasikan heap maksimal K item dengan *worst candidate* di head. Buat oracle terpisah dengan full-sort seluruh account balances (hanya pada test). Jalankan minimal **100 dataset seeded**, termasuk `k=0`, `k>a`, tie absolut, transaksi duplikat, dan data kosong. Bandingkan **urutan dan nilai**, bukan hanya Set hasil.

**Tahap D — complexity dan lint.** Catat `n`, `u`, `a`, `k`, time/space untuk setiap struktur. Jalankan berikut pada source latihan, termasuk dependencies yang diperlukan dalam satu invocation:

~~~sh
javac -Xlint:rawtypes -Xlint:unchecked -Werror *.java
~~~

Hasil harus tanpa raw-type maupun unchecked warning. Jangan menutup warning memakai `@SuppressWarnings` sebagai cara lulus latihan.
