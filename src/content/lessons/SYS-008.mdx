<LessonStage stage="understand">

> **Problem:** frontend membutuhkan API transfer dengan request, response, status, dan error yang stabil, walaupun implementasi controller, service dan database bisa berubah.

**Mulai:** tulis kontrak tiga operasi terlebih dahulu: `POST /transfers`, `GET /transfers/{id}`, dan `GET /accounts/{id}`. Jangan membuat controller sebelum semua respons observable disepakati.

<MentalModel title="API design = observable contract, bukan implementasi transaksi">

- **Resource:** `POST /transfers` membuat resource transfer; `GET` mengambil representasi transfer atau account. Resource HTTP bukan otomatis satu tabel database.
- **Request DTO:** `clientReference`, `sourceAccountId`, `destinationAccountId`, `amount` sebagai **decimal string**, dan `currency` (`IDR`/`USD`).
- **201 Created:** transfer resource tercipta dan `Location` menunjuk URI-nya; **tidak membuktikan dana sudah settled**.
- **Error contract:** kode HTTP mengungkap kategori kegagalan; RFC 9457 `application/problem+json` memberi `type`, `title`, `status`, dan `detail` yang aman.
- **Security:** `401` berarti credentials hilang/tidak valid dan membutuhkan `WWW-Authenticate`; `403` berarti identitas valid tetapi operasi ditolak.
- **Compatibility:** field respons baru yang opsional dapat bersifat additive, tetapi tetap perlu diuji terhadap consumer lama.

</MentalModel>

## Resource dan response matrix

| Endpoint | Success | Kegagalan yang dimodelkan |
| --- | --- | --- |
| `POST /transfers` | **201** + `Location` + Transfer | **400, 401, 403, 409, 500** |
| `GET /transfers/{id}` | **200** + Transfer | **401, 403, 404, 500** |
| `GET /accounts/{id}` | **200** + Account | **401, 403, 404, 500** |

Kebijakan lab: `409` berarti **clientReference** sudah digunakan. Itu keputusan desain yang harus benar-benar diimplementasikan sebelum dipakai; dokumen tidak membuktikan *idempotent retries*, deduplikasi transaksi atau pemrosesan tepat sekali.

### Contoh POST request

~~~http
POST /transfers HTTP/1.1
Authorization: Bearer <demo-token>
Content-Type: application/json
Accept: application/json

{
  "clientReference": "client-ref-001",
  "sourceAccountId": "acc-01",
  "destinationAccountId": "acc-02",
  "amount": "125000.00",
  "currency": "IDR"
}
~~~

### Contoh 201 Created

~~~http
HTTP/1.1 201 Created
Location: /transfers/tr-001
Content-Type: application/json

{
  "transferId": "tr-001",
  "clientReference": "client-ref-001",
  "sourceAccountId": "acc-01",
  "destinationAccountId": "acc-02",
  "amount": "125000.00",
  "currency": "IDR",
  "status": "PENDING",
  "createdAt": "2026-11-06T08:00:00Z"
}
~~~

Contoh ini memodelkan response; tidak ada bearer token sungguhan, service di-deploy, atau database yang diakses.

## Desain failure: jangan tertukar 400 / 401 / 403 / 409 / 500

| Status | Kapan digunakan pada kontrak latihan | Yang dilakukan client |
| --- | --- | --- |
| **400** | JSON/field amount atau ID tidak valid | Perbaiki payload |
| **401** | Bearer token hilang atau invalid | Ikuti `WWW-Authenticate` challenge |
| **403** | Sudah authenticated, tidak berhak mengakses akun | Jangan otomatis mengulang dengan token identik |
| **404** | Transfer/account ID tidak ditemukan | Periksa resource ID; kebijakan concealment harus konsisten |
| **409** | `clientReference` telah dipakai (kebijakan lab) | Selidiki konflik; jangan membuat referensi baru secara buta |
| **500** | Server mengalami kondisi tidak terduga | Tampilkan pesan aman; jangan tampilkan stack trace |

Contoh problem detail untuk konflik:

~~~http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "urn:cs101:problem:reference-conflict",
  "title": "Client reference conflict",
  "status": 409,
  "detail": "The clientReference is already in use."
}
~~~

Untuk 401, gunakan `WWW-Authenticate: Bearer realm="transfers"` beserta status 401. `urn:cs101:problem:...` adalah identifier contoh yang **tidak dirancang untuk dereference**. Konsumen memakai `type` dan status, bukan parsing dari `detail` yang bisa berubah.

## Project — Transfer API Spec

<LearningSegments stage="evidence" segments={lessonSegments} />

Bandingkan dua response berikut dari perspektif **client versi lama**:

~~~json
{
  "transferId": "tr-001",
  "amount": "125000.00",
  "currency": "IDR"
}
~~~

Versi selanjutnya menambahkan `"description": "Transfer antar akun"` sebagai properti **opsional** dan tetap mempertahankan semua field wajib lainnya. Perubahan `"amount": "125000.00"` menjadi `"amount": 125000` adalah **breaking type change**. Kedua cuplikan di atas disederhanakan untuk pembahasan; full request/response tetap harus mengikuti field wajib dalam file OpenAPI.
